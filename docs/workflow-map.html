How a new component's tokens travel, today and tomorrow

3 maps of the same job: giving a new component its colour tokens. The first is how we work now. The second is the flow the current PRD describes. The third moves token creation back into Figma, with the plugin doing the naming, creating and re-applying, and the tool acting as the record and the route to code.

Map 1

Today, without the tool

Exploring with a mix of primitives and semantic tokens is right at this stage. The trouble starts once the colours are settled: every name is worked out from the docs, typed twice, mapped by hand, applied by hand and then handed over as a screenshot.

Names typed by hand: 3 times (notes, Figma variables, CSS)Route back from code: none, so drift goes unnoticed
Map 2

With the tool as the PRD describes it

The naming help, the pull request and the review of developer changes are real gains. But the designer has to leave Figma in the middle of building the component, copy the colours across by reading them off the canvas, sync the new variables back into Figma and then re-apply them by hand before the pull request goes out. The tool saves making the variables, not applying them. The manual work has moved, not gone.

Names typed by hand: 1 time (in the tool)Colours copied by eye from Figma: every oneRe-applying to layers: by hand, once; later syncs need none
Map 3

Proposed: create in Figma, record in the tool

The designer stays in Figma until the component is finished. The plugin scans the light and dark frames and proposes the tokens and where each one is used. You accept the names and publish the variables, then apply them to the layers as a separate step. Then it sends the new tokens to the tool, which flags them and pushes them to code. Quick edits to existing tokens still happen in the tool.

Every component token points to a primitive, as agreed on 23 Nov 2026. A part that used content-default gets the primitive behind it in each mode, so a later change to content-default does not change the control. Dark values come from the dark duplicate. Categories: the frame's own fill → surface, its stroke → line, layers named surface, line, content or icon → that category, anything inside an instance such as an icon → content. Review

Will it work in practice?

Checked against what a Figma plugin can do on the Pro plan and what the tool already has.

Reading the colours on a selection

Works

A plugin can walk every layer in the selected frames and read each fill, stroke and text colour, and whether it is a raw value or bound to a variable. This is standard plugin access, not an Enterprise feature.

Pairing the light and dark frames

Agreed

The dark frame is always a duplicate of the light one, with only the colours changed, so the plugin pairs layers by their position in the frame. Anything that does not line up is still flagged, in case a layer was added to 1 frame only.

Guessing category, role and state

Test run needed

The plugin reuses the tool's naming rules: the 4 categories, the suggested roles and states, and no focus tokens. Category comes from the layer. State comes from the option chosen in the State property, the part after the = in State=Hover. An option the rules do not know is flagged as a possible new state, so a test run on a few real components will show the edge cases.

Keeping the "never mix" rule

Works

If any layer needs a component token, the plugin proposes a full component set. Parts that used a semantic token become component tokens that point to the primitive behind it, as agreed on 23 Nov 2026.

Creating the variables

Already built

Phase 5 already creates variables with light and dark modes, aliases and hidden non-default states. The scan would reuse that code and the same naming rules engine the tool uses, so names are checked the same way in both places.

Binding the new tokens back onto the layers

Works

A plugin can bind a variable to a fill or stroke, so it can swap each raw colour for its new token in both frames. One catch: layers inside nested instances (an icon component inside the control) become overrides, so the plugin should list those for you to check.

Sending new tokens to the tool

New work

Today the plugin only reads tokens from the tool and reports a sync back. It already signs in with a key, so adding a "send new tokens" route is a modest extension. They arrive in the tool as drafts marked "From Figma", with the component and your name.

Publishing the Figma library

Stays manual

Plugins cannot press Figma's own library Publish button. The variables exist in the file straight away, but other files only see them after you publish the library, as now.

Clashes while you work

Needs a rule

Someone could add a token with the same name in the tool, or edit a variable directly in Figma. The tool should flag a name that already exists when the drafts arrive, and the plugin's sync shows any Figma edit that does not match the tool.

Do later syncs undo the bindings?

No

When developers tune a value, or a token is renamed, the plugin updates the same Figma variable in place, so every layer bound to it changes on its own. Only 2 cases break a binding: a deprecated token is removed (layers keep the colour but lose the link), or a token changes type, which never happens to a colour.

Quick edits to existing tokens

No change

Changing a value, renaming or deprecating stays in the tool, where it is quickest. This plan adds a second way in for new component tokens; it does not replace the tool's creation flow.

Effect on the plan

What would change in the PRD

Source of truth, reworded

The tool stays the record: nothing reaches code without passing through it, and every decision is logged there. Figma becomes the place where new component tokens are drafted. This keeps the PRD's goals, and drops the line "a token change always starts in the tool".

  • End-to-end workflow gains a second entry route: "Create in Figma, send to the tool" next to "Create in the tool".
  • Component scan (F12) already exists in the PRD and is mostly built (23 Nov 2026). It is updated, colour only: read dark values from the dark duplicate, then accept names, save and publish, apply to layers and send to the tool as separate steps.
  • Tokens arrive in the tool as drafts marked "new from Figma", ready for a designer to review and push.
  • Hand-off screenshot is replaced by the pull request and its changelog.
Agreed 24 Nov 2026

Decisions made

  1. The dark frame is always a duplicate of the light frame, with only the colours changed.
  2. Category, role and state come from the tool's existing naming rules. Edge cases, such as new interactive states, will be found by a test run.
  3. You accept the names in the plugin, then save and publish the variables to Figma. Applying them to the layers is a separate step after that.
  4. Any designer can review tokens that arrive from Figma before they are pushed to code.
  5. The scan covers colour only for now.
  6. Component tokens always point to a primitive, never to a semantic token (kept from 23 Nov 2026).
  7. This builds on the Component scan work from 23 Nov 2026, not a new branch.
